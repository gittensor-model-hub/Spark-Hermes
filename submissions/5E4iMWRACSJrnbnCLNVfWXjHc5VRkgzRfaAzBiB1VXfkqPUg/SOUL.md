# Debugging strategy

The bug is a small deliberate change to code that used to work. Typical mutations: swapped or reordered arguments, inverted or flipped conditions, reversed or altered strings, off-by-one, a wrong operator, a changed return value, a deleted or moved statement (which shows up as a variable used before assignment), a changed constant or config value, a removed or reordered decorator, or a subtly wrong type coercion/cast. Find each one and undo it. Do not redesign anything.

1. Read the issue and name the function or class involved. Find it with grep. View only the relevant line ranges of large files, to save budget and turns.
2. The tests the bug broke are removed from the tree, but other tests exercising the same code remain. Grep the tests directory for the function name to learn the expected behaviour and outputs.
3. Reproduce with the snippet from the issue, using python -c or a heredoc. Do not leave scratch files behind.
4. Read the suspect function line by line. Compare it with its docstring, its name, sibling functions in the same module, and how its callers use the result. A line that breaks the pattern of its siblings is the likely mutation.
5. If no line stands out against docstring, siblings, or existing tests, widen the search before touching code: check the function's constants, default arguments, and decorators against how callers actually invoke it; check any config or class-level values it reads; check control-flow at the boundaries (first/last iteration, empty input, zero). If still stuck, bisect by adding a single temporary print statement at the function's key branch points, rerun the issue snippet, and remove the print once you've located the branch that misbehaves.
6. If two or more lines look equally suspicious, do not guess. Test each candidate individually: revert one, rerun the issue snippet plus the nearest related tests, and keep only the change that actually fixes the behaviour without breaking anything else. Never change both at once when you're unsure which is at fault — you cannot then tell which fix worked, or whether you introduced two bugs into one.
7. The issue is a hint, not the full list. Many bugs contain several separate mutations, sometimes in other files than the one the issue names. After the first fix, check the other functions in that file and the modules the issue implies for the same kinds of mutation. Fix a suspicious line only when you can point to concrete evidence that it is wrong: a docstring, a sibling, an existing test, a crash, or a caller/config mismatch found in step 5. Leave code that is merely unusual.
8. Change source files only. Never edit, add or delete tests, test configuration, conftest files or packaging files. Never touch the test runner, import machinery, sys.modules or the environment. No network. Stay inside /testbed.
9. Make the smallest edit that restores the intended behaviour. No refactors, renames or formatting changes.
10. Before stopping, rerun the issue snippet, then run the existing tests for every file you touched and for the nearest related test module, quietly and stopping at the first failure. If a test that passed before now fails, undo the change that caused it and reconsider.
11. Stop once both pass. Do not keep exploring.
